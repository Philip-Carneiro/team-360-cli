# team-360-cli

A CLI tool that generates comprehensive 360-degree status reports for your team's JIRA board and publishes them to Confluence.

It pulls data from multiple sources (JIRA, GitHub, GitLab, Google Calendar), applies heuristics to surface risks and blockers, compares against the previous report to show deltas, and publishes a ready-to-share status page on Confluence. No AI tokens required.

## What It Does

1. **Collects** data in parallel from your team's JIRA board (active work, backlog, bugs, strats, completed tickets, epic progress), GitHub PRs, GitLab MRs, and Google Calendar (PTO/absences)
2. **Analyzes** the data with heuristics: stale ticket detection, workload distribution, activity type breakdown, testing pipeline health, epic completion tracking
3. **Compares** against the previous 360 report to generate delta columns (what changed since last report)
4. **Publishes** the report to Confluence (archiving the previous one), saves a local markdown copy, and optionally saves to an Obsidian vault



## Prerequisites

- Python 3.10+
- `gh` [CLI](https://cli.github.com/) — authenticated (`gh auth login`)
- `glab` [CLI](https://gitlab.com/gitlab-org/cli) — authenticated, only if using GitLab
- Google Calendar API credentials — only if collecting PTO/absence data



## Security

No tokens or credentials are stored in the repository. All secrets come from environment variables:

- JIRA/Confluence: env vars (`JIRA_API_TOKEN`, etc.)
- GitHub: `gh` CLI handles auth via its own keychain
- GitLab: `glab` CLI handles auth, plus optional `GITLAB_TOKEN` env var
- Google Calendar: env vars (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_REFRESH_TOKEN`), with fallback to `~/.config/google-calendar-token.json` for local dev

The `.gitignore` excludes `.env` files, token files, and generated reports. Never commit credentials to this repo.

Run `python main.py --setup` for an interactive wizard that sets these up and verifies connectivity.

| ---------------------- | ------------------------------------------------------------------------------- |
| `OBSIDIAN_VAULT`       | Path to Obsidian vault — reports are saved under `SCRUMBAN/STATUS/360/`         |

| `GITLAB_TOKEN`         | GitLab API token                                                                |
| `GOOGLE_CLIENT_ID`     | Google OAuth client ID (for Calendar API)                                       |
| `GOOGLE_CLIENT_SECRET` | Google OAuth client secret                                                      |
| `GOOGLE_REFRESH_TOKEN` | Google OAuth refresh token — if all three are set, the token file is not needed |




## Team Configuration

The easiest way to add a team is with the interactive wizard:

```bash
python3 main.py --add-team
```

It prompts for each field, verifies that the Confluence pages are accessible, and saves to `teams.json`. It also runs automatically at the end of `--setup`.

Teams are stored in `teams.json`, which is **generated by** `--setup` **or** `--add-team` and gitignored (it contains your org-specific URLs). A `teams.example.json` is included as reference. Each key is a team name:

```json
{
  "My Team": {
    "team_md": "https://your-org.atlassian.net/wiki/spaces/TEAM/pages/123/Team+Overview",
    "jira_md": "https://your-org.atlassian.net/wiki/spaces/TEAM/pages/456/Jira+Reference",
    "confluence_md": "https://your-org.atlassian.net/wiki/spaces/TEAM/pages/789/Confluence+Reference",
    "jira_projects": "MYPROJ,OTHERPROJ"
  }
}
```


| Field           | Required | Description                                                                                                                                          |
| --------------- | -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `team_md`       | Yes      | Confluence page with roster, boards, JIRA label, cadence                                                                                             |
| `jira_md`       | Yes      | Confluence page with JIRA projects, JQL templates, repo mapping                                                                                      |
| `confluence_md` | Yes      | Confluence page with 360 report folder IDs                                                                                                           |
| `jira_projects` | No       | Comma-separated JIRA project keys (e.g. `MYPROJ,OTHERPROJ`). Used for swimlane discovery and JQL queries. If omitted, parsed from the `jira_md` page |


All `*_md` fields accept a Confluence page URL, a bare page ID, or `"local"` to read from a local markdown file instead.

See the [`examples/`](examples/) directory for complete examples of each page:

- [`examples/team.md`](examples/team.md) — roster, boards, JIRA label, cadence, activity targets, PTO calendars
- [`examples/jira.md`](examples/jira.md) — JIRA projects, JQL templates, repository mapping
- [`examples/confluence.md`](examples/confluence.md) — 360 report folder IDs

These match the exact format the parser expects. You can use them as Confluence pages or as local files in a workspace directory:

```
workspace/
  team.md              # copy of examples/team.md, customized
  context/
    jira.md            # copy of examples/jira.md, customized
    confluence.md      # copy of examples/confluence.md, customized
```



## Getting Started



### Step 1: Install

```bash
git clone https://github.com/your-org/team-360-cli.git
cd team-360-cli
pip install -r requirements.txt
```



### Step 2: Setup credentials

Run the interactive setup wizard. It walks through each required env var, verifies connectivity to JIRA and Confluence, and optionally appends the exports to your `~/.zshrc`:

```bash
python3 main.py --setup
```

The wizard will:

1. Check which env vars are already set (skips those)
2. Prompt for any missing ones (JIRA, Confluence, GitLab, Google Calendar)
3. Verify JIRA and Confluence connectivity
4. Offer to append new exports to `~/.zshrc`
5. Offer to add your first team (see next step)



### Step 3: Add a team

Add a team interactively. The wizard prompts for each Confluence page, verifies access, and saves to `teams.json`:

```bash
python3 main.py --add-team
```

The wizard will:

1. Ask for the team name
2. Prompt for each Confluence page (team overview, JIRA reference, Confluence reference)
3. Optionally ask for JIRA project keys (used for swimlane discovery)
4. **Verify each Confluence page is accessible** — shows the page title on success or an error on failure
5. Ask if you want to save (even if some pages failed verification)
6. Ask if you want to add another team

You can run `--add-team` anytime to add more teams or update existing ones.

### Step 4: Verify everything works

```bash
python3 main.py --check
```

Runs a full health check: env vars, JIRA/Confluence/GitHub/GitLab connectivity, team config parsing, and Google Calendar access. Fix any failures before generating reports.

### Step 5: Generate a report

```bash
# Test run first (safe — no archiving, adds -test suffix)
python3 main.py --team "my team" --swimlane all --test

# Production report (publishes to Confluence and archives previous)
python3 main.py --team "my team" --swimlane all
```



## Commands



### `--setup` — First-time setup

```bash
python3 main.py --setup
```

Interactive wizard that configures all environment variables and verifies connectivity. Walks through each credential (JIRA, Confluence, GitLab, Google Calendar), tests the connection, and offers to append exports to `~/.zshrc`. At the end, offers to add your first team.

### `--add-team` — Add or update a team

```bash
python3 main.py --add-team
```

Interactive wizard to configure a team in `teams.json`. Prompts for:

- **Team name**
- **Team overview page** — Confluence page with roster, boards, JIRA label
- **JIRA reference page** — Confluence page with projects, JQL, repo mapping
- **Confluence reference page** — Confluence page with 360 folder IDs
- **JIRA project keys** (optional) — e.g. `MYPROJ,OTHERPROJ`, used for swimlane discovery

After collecting all fields, **verifies each Confluence page is accessible** (shows page title on success or error on failure). If verification fails, asks whether to save anyway. After saving, asks if you want to add another team.

### `--check` — Health check

```bash
python3 main.py --check
```

Runs a full diagnostic of your setup. Verifies:

1. **Environment variables** — checks all required and optional env vars are set
2. **Service connectivity** — tests JIRA login, Confluence API, GitHub CLI (`gh`), GitLab CLI (`glab`)
3. **Team configuration** — checks `teams.json` exists, then for each team:
  - Verifies each Confluence page is accessible (shows page title)
  - Parses the team config and reports: team name, roster size, boards, JIRA label, JIRA projects
  - Warns about missing or incomplete fields
4. **Google Calendar** — refreshes the OAuth token, then for each configured PTO calendar, fetches the last 30 days and reports event count
5. **Obsidian vault** — checks the path exists

Outputs a summary: `N/M passed, X failed, Y skipped`.

### `team-prs` — PR tracker report

```bash
python3 team_prs.py
python3 team_prs.py --team "my team"
```

Generates a report of all open PRs for the team, collected from both GitHub repos (via `gh` CLI) and JIRA ticket PR links. The report includes:

- **Open PRs grouped by team member** — each roster member gets a section with their PRs
- **PR age summary table** — all PRs sorted by days open, with clickable links
- **Deduplication** — same PR found in both GitHub and JIRA appears only once

Requires a complete setup (`--setup` + `--add-team`). If setup is incomplete, offers to run it.

Reports are saved to `Team-PRs-Report/YYYY/Month/` with timestamped filenames:

```
Team-PRs-Report/
  2026/
    August/
      [24-08-2026 - 14:30:00] - PRs Tracker Report.md
    September/
      [15-09-2026 - 09:00:00] - PRs Tracker Report.md
```

### Report generation

```bash
python3 main.py [OPTIONS]
```


| Flag                 | Description                                                                 | Default            |
| -------------------- | --------------------------------------------------------------------------- | ------------------ |
| `--team <name>`      | Team name (substring match), or `all` for every team in `teams.json`        | Interactive prompt |
| `--swimlane <value>` | `all` = no filter, `ask` = interactive, or Epic key                         | `ask`              |
| `--test`             | Test mode — adds `-test` suffix, skips archiving previous 360 on Confluence | off                |
| `--suffix <str>`     | Extra suffix for filename (e.g. `2` produces `-test-2`)                     | none               |
| `--workspace <path>` | Path to local workspace dir (instead of `teams.json`)                       | current dir        |
| `-v`, `--verbose`    | Debug logging                                                               | off                |




### Interactive Prompts

When running without `--team` or `--swimlane`, the CLI prompts interactively with a **60-second timeout** that defaults to "All" on both selections.

**Team selection** (when multiple teams in `teams.json`):

```
Available teams:
  1. Frontend Team
  2. Backend Team
  3. All teams

Select team [1-3] (defaults to All in 60s):
```

If "All teams" is selected (or timeout), the report runs sequentially for each team.

**Swimlane selection** (per team):

```
Swimlanes (parent Epics):
  1. PROJ-100 — Backend Refactor (12 tickets)
  2. PROJ-200 — New Dashboard (8 tickets)
  3. PROJ-300 — Bug Fixes (5 tickets)
  4. All swimlanes (25 tickets)

Select swimlane [1-4] (defaults to All in 60s):
```

Both prompts timeout after 60 seconds and default to "All". This makes `python3 main.py` fully unattended-safe — just let it sit and it runs everything.

### Examples

```bash
# Fully interactive — prompts for team and swimlane (defaults to All after 60s)
python3 main.py

# All teams, all swimlanes (no prompts)
python3 main.py --team all --swimlane all

# Single team, all swimlanes
python3 main.py --team "my team" --swimlane all

# Test run with verbose logging (safe — doesn't archive anything)
python3 main.py --team "my team" --swimlane all --test -v

# Filter to a specific swimlane by Epic key
python3 main.py --team "my team" --swimlane "Release 2.0"

# Multiple test runs in the same day (suffix avoids filename collision)
python3 main.py --team "my team" --test --suffix 2

# Use local markdown files instead of Confluence pages
python3 main.py --workspace /path/to/workspace --swimlane all
```



### Test Mode vs Production


|              | Test (`--test`)                                                     | Production (default)                                  |
| ------------ | ------------------------------------------------------------------- | ----------------------------------------------------- |
| Local report | `reports/` with `-test` suffix                                      | `reports/`                                            |
| Vault        | Saved with `-test` suffix                                           | Saved normally                                        |
| Confluence   | Creates page with `test-` prefix, does **not** archive previous 360 | Creates page and archives previous 360 to Past folder |


Always run `--test` first to validate the report before generating the production version.

## Output

Reports are saved to `reports/team-360-status/` locally, and optionally to the Obsidian vault and Confluence. Filenames follow the pattern:

<emoji> <Team> 360 - DD-MM-YYYY.md

## Hosting & Automated Runs (Cron)

The script is designed to run unattended. Use `--team` and `--swimlane all` to skip interactive prompts.

### Option 1: Linux/Mac server with cron

1. Clone the repo and install dependencies:

```bash
git clone https://github.com/your-org/team-360-cli.git /opt/team-360-cli
cd /opt/team-360-cli
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

1. Install and authenticate CLIs:

```bash
# GitHub CLI
gh auth login

# GitLab CLI (if needed)
glab auth login --hostname gitlab.example.com
```

1. Create an env file at `/opt/team-360-cli/.env`:

```bash
export JIRA_BASE_URL="https://your-org.atlassian.net"
export JIRA_EMAIL="you@example.com"
export JIRA_API_TOKEN="your-jira-token"
export CONFLUENCE_URL="https://your-org.atlassian.net/wiki"
export CONFLUENCE_USERNAME="you@example.com"
export CONFLUENCE_API_TOKEN="your-confluence-token"
export OBSIDIAN_VAULT="/path/to/vault"
export GITLAB_HOST="gitlab.example.com"
export GOOGLE_CLIENT_ID="your-client-id.apps.googleusercontent.com"
export GOOGLE_CLIENT_SECRET="your-client-secret"
export GOOGLE_REFRESH_TOKEN="your-refresh-token"
```

1. Create a wrapper script at `/opt/team-360-cli/run-360.sh`:

```bash
#!/bin/bash
set -euo pipefail
cd /opt/team-360-cli
source .env
source .venv/bin/activate
python main.py --team "my team" --swimlane all 2>&1 | tee "reports/cron-$(date +%Y%m%d).log"
```

```bash
chmod +x /opt/team-360-cli/run-360.sh
```

1. Add crontab entry (`crontab -e`):

```cron
# Run every weekday at 9:00 AM UTC
0 9 * * 1-5 /opt/team-360-cli/run-360.sh

# Or twice a week (Monday and Thursday)
0 9 * * 1,4 /opt/team-360-cli/run-360.sh
```



### Option 2: Docker container

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
RUN apt-get update && apt-get install -y curl git && \
    curl -fsSL https://cli.github.com/packages/githubcli-archive-keyring.gpg | dd of=/usr/share/keyrings/githubcli-archive-keyring.gpg && \
    echo "deb [arch=$(dpkg --print-architecture) signed-by=/usr/share/keyrings/githubcli-archive-keyring.gpg] https://cli.github.com/packages stable main" | tee /etc/apt/sources.list.d/github-cli.list && \
    apt-get update && apt-get install -y gh && \
    apt-get clean
COPY . .
ENTRYPOINT ["python", "main.py", "--swimlane", "all"]
```

Run with env vars passed at runtime:

```bash
docker run --rm \
  -e JIRA_BASE_URL -e JIRA_EMAIL -e JIRA_API_TOKEN \
  -e CONFLUENCE_URL -e CONFLUENCE_USERNAME -e CONFLUENCE_API_TOKEN \
  -e GOOGLE_CLIENT_ID -e GOOGLE_CLIENT_SECRET -e GOOGLE_REFRESH_TOKEN \
  -v /path/to/reports:/app/reports \
  team-360-cli --team "my team"
```

Schedule via cron, systemd timer, or any container orchestrator (Kubernetes CronJob, AWS ECS Scheduled Task, etc.).

### Option 3: GitHub Actions (scheduled workflow)

This repository includes two production workflows. See the **Workflows Included** section below for details on enabling them in your fork.

### Key Points for Unattended Runs

- Always pass `--team <name>` and `--swimlane all` to avoid interactive prompts
- The `gh` CLI needs a valid auth token in the environment (`GH_TOKEN` or `gh auth login`)
- Google Calendar: set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and `GOOGLE_REFRESH_TOKEN` as env vars (or secrets in CI). Locally, the token file at `~/.config/google-calendar-token.json` also works as fallback. The initial OAuth flow is interactive (do it once manually to get the refresh token)
- Confluence publishing happens automatically if `confluence_root_dir_id` is set in the team config
- Use `--test` for dry runs that don't archive previous reports on Confluence


## Workflows Included (Running in Your Fork)

This repository includes two production GitHub Actions workflows that run scheduled reports and post results to Slack. If you fork this repo and want to use them, follow the setup instructions below.

### 1. Daily PRs Report → Slack

**File:** `.github/workflows/daily-prs-slack.yml`

**What it does:** Generates a daily report of open PRs with review status and posts it to Slack.

**Schedule:** `0 6 * * 1-5` (6:00 AM UTC, Monday-Friday)

**Secrets required:**
- `TEAMS_JSON` — team configuration (same format as local `teams.json`)
- `JIRA_BASE_URL` — Jira instance URL
- `JIRA_EMAIL` — Jira account email
- `JIRA_API_TOKEN` — Jira API token
- `SLACK_WEBHOOK_URL` — Slack webhook for daily PR reports
- `SLACK_WEBHOOK_URL_ALERTS` — Slack webhook for failure alerts (optional but recommended)

### 2. Weekly 360 Report → Confluence + Slack

**File:** `.github/workflows/weekly-360.yml`

**What it does:** Generates a comprehensive 360 report, publishes it to Confluence, and posts the link to Slack.

**Schedule:** `0 5 * * 4` (5:00 AM UTC, every Thursday)

**Manual trigger:** Supports `workflow_dispatch` with a `test_mode` input for dry runs.

**Secrets required:**
- `TEAMS_JSON` — team configuration
- `JIRA_BASE_URL` — Jira instance URL
- `JIRA_EMAIL` — Jira account email
- `JIRA_API_TOKEN` — Jira API token (also used for Confluence auth)
- `GOOGLE_CLIENT_ID` — Google OAuth client ID (for Calendar integration)
- `GOOGLE_CLIENT_SECRET` — Google OAuth client secret
- `GOOGLE_REFRESH_TOKEN` — Google OAuth refresh token
- `SLACK_WEBHOOK_URL_360_REPORT` — Slack webhook for posting the Confluence link
- `SLACK_WEBHOOK_URL_ALERTS` — Slack webhook for failure alerts (optional but recommended)

### Enabling Workflows in Your Fork

1. **Enable Actions:** Go to the Actions tab in your fork and click "I understand my workflows, go ahead and enable them."

2. **Add secrets:** Go to Settings > Secrets and variables > Actions, and add all the required secrets listed above for the workflows you want to use.

   - **`SLACK_WEBHOOK_URL_ALERTS`** is the dedicated failure-alert webhook. When a workflow fails (e.g., invalid credentials, API errors, network issues), the failure notification is sent here instead of the regular report channels. This keeps your primary Slack channels clean and ensures critical alerts are not missed.

3. **Preflight validation:** Both workflows run a preflight check before doing any work. If a credential is invalid or expired, the workflow fails fast and sends an alert to `SLACK_WEBHOOK_URL_ALERTS` with details:
   - HTTP 401: Invalid or expired credential
   - HTTP 403: Access denied
   - For Google OAuth: response body includes `invalid_grant` when the refresh token is expired or revoked

4. **Manual runs and schedule customization:**
   - Both workflows support manual triggering via `workflow_dispatch` (Actions tab > workflow > Run workflow).
   - To adjust the schedule, edit the `cron:` line in the workflow file.
   - The weekly workflow has a `test_mode` input for dry runs that won't archive previous reports.

### Failure Alerts

When any step in a workflow fails, the final step posts a failure alert to the `SLACK_WEBHOOK_URL_ALERTS` webhook. The alert includes:
- Workflow name, repository, job name
- GitHub Actions run URL (for logs)
- Branch and commit SHA
- If the failure was in the preflight check: the specific credential error (e.g., "FAIL google: HTTP 401 (invalid Google OAuth credentials; refresh token expired/revoked)")

This ensures you are immediately notified of workflow failures and can take action (e.g., renew an expired token, fix a credential) without waiting for the next scheduled run.
